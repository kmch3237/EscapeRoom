## 관찰된 약점 / 습관 (솔직하게)

### 1. 입력(재료) vs 출력(결과) 구분이 약하다
- "전체 페이지 수만 받으면 되는 거 아냐?"라며 **계산 결과를 파라미터로 받으려** 했다.
- 결과를 입력으로 넣으면 그 메서드는 존재 이유가 없어진다.
- **고치는 법:** 메서드 짤 때 "이미 알아서 넣어주는 게 입력 / 그걸로 새로 알아내는 게 출력"으로 항상 나눠 생각.

### 2. 몫(`/`) vs 나머지(`%`)를 반복해서 혼동
- "남는 게 있냐"를 판단해야 하는 자리에 자꾸 `/`(몫)를 썼다. 판단 기준은 `%`(나머지).
- `/` = 꽉 찬 페이지 수, `%` = 마지막 자투리(있으면 페이지 +1).

### 3. 삼항연산자 문법 미숙
- `?` 앞 조건 자리에 숫자(`pageData/size`)나 `if(...)`를 넣었다. 조건은 **참/거짓(boolean)** 이어야 한다.
- `=`(대입)와 `==`(비교)를 혼동.
- `if`(문장)와 `? :`(값을 내는 식)는 같은 일을 하는 다른 도구 → 같이 쓰면 안 됨.

### 4. 특수 케이스를 일반 공식으로 흡수하지 못함
- 데이터가 적은 경우를 자꾸 별도 `if`로 따로 처리하려 했는데, `%` 공식 하나로 0개·5개·20개·23개가 전부 자동 해결됨.
- **고치는 법:** 특수 케이스를 if로 막기 전에 "일반 공식이 이 경우도 자연히 커버하나?" 먼저 확인.

### 5. 코드 진입점("어디서부터 짜지")을 어려워함
- 배운 사고법: ①return 타입 → ②파라미터 → ③로직 → ④return. 껍데기(시그니처) 먼저, 로직은 빈칸 채우기.

### 6. 워크플로: 저장(Cmd+S) 누락
- 고쳤다고 했는데 파일은 그대로인 경우가 있었음. 수정 후 저장 확인 습관.

## 오늘 배운 핵심 개념 (면접용)

### A. 테마 SQL 슬라이스 (getThemeList 직접 재작성)
- JOIN ON = 두 테이블을 공통 컬럼(FK=PK)으로 연결. `=` 양쪽이 서로 다른 테이블이어야 함.
- 페이징: `ORDER BY`(필수) + `OFFSET n ROWS FETCH NEXT m ROWS ONLY`. n = 오늘 짠 offset 공식 결과.
- `#{}` vs `${}` (★면접 1순위): `#{}`=PreparedStatement 바인드변수(`?`), 값과 쿼리 분리 → SQL Injection 방어. `${}`=문자열 그대로 치환 → 위험. **값은 `#{}`, 컬럼명·정렬기준은 `${}`(불가피) + 화이트리스트로 방어.**
- 동적 SQL `<where>`+`<if>`: 검색어 있을 때만 조건 붙이고, 맨 앞 AND/OR 자동 제거.
- 커서 페이징 vs OFFSET: OFFSET은 앞 N개를 세고 버려 깊은 페이지가 느림. 커서(`ROOM_ID < lastId` + FETCH FIRST)는 인덱스로 점프해 빠름 → 무한스크롤엔 커서.

### B. 예약 슬라이스 동시성 (PRC_RESERVATION 프로시저)
- 예약 검증·트랜잭션·동시성 전부 오라클 프로시저에 있음. 그래서 자바 서비스에 `@Transactional` 없음(PL/SQL이 COMMIT/ROLLBACK 직접).
- **동시성 핵심**: `SELECT ... FOR UPDATE`로 슬롯 행에 비관적 락 → 동시 요청 직렬화. 먼저 잡은 쪽이 커밋하면 뒤 요청은 `NOT EXISTS` 검증에서 중복 발견해 거부 → 한 슬롯에 예약 하나만.
- 검증 실패마다 커스텀 EXCEPTION + ROLLBACK + `RAISE_APPLICATION_ERROR(-200xx,'메시지')`. 컨트롤러가 `DataAccessException`에서 ORA 메시지 파싱해 사용자에게 표시.

### C. 프로시저를 쓰는 게 맞나 / 실무 기준 (★토론형 면접)
- **장점**: 데이터 중심 검증을 한 트랜잭션·한 왕복에 처리, DB가 정합성 강하게 보장.
- **단점**: 로직이 DB에 묻혀 테스트·버전관리·디버깅 어려움, DB 종속(이식성↓), 자바 서비스가 빈 껍데기.
- **실무에서 프로시저 쓰는 경우**: 대량 배치·집합연산, 고성능(왕복 최소화), 여러 앱이 한 DB 공유, 금융/공공/레거시(DBA 소유 문화).
- **안 쓰는 경우**: 일반 웹/스타트업/MSA — 로직은 앱 레이어(`@Transactional`+`FOR UPDATE`), 테스트·이식성 위해. ORM(JPA)은 프로시저 비권장.
- 한 줄: "데이터에 가까울수록 빠르지만, 코드에 가까울수록 관리하기 좋다."
- 포트폴리오 멘트: "팀은 프로시저로 동시성 처리, 나는 그 원리를 이해했고 서비스 레이어 `@Transactional`+`FOR UPDATE`로도 구현 가능하다."

### D. 의존성 주입(DI) — 왜 new 안 쓰고 스프링이 주입하나 (★면접 단골)
- 컨트롤러 패턴: `@Controller @Slf4j @RequiredArgsConstructor` + `private final ReservationService service;`
  - `@RequiredArgsConstructor`(Lombok) = final 필드를 받는 생성자 자동 생성 → 스프링이 그 생성자로 빈을 주입(생성자 주입).
  - `@Slf4j` = log 로거 자동 생성. `@Controller`/`@Service` = 빈 등록.
- **직접 new 하면 불편한 점 3가지:**
  1. 의존 사슬을 다 손으로 조립해야 함 (서비스→매퍼→SqlSession→DataSource). DI는 스프링이 이 그래프를 자동 조립.
  2. 객체 중복 — 컨트롤러마다 new 하면 같은 서비스가 복제됨. 스프링은 싱글톤 하나를 공유.
  3. 특정 구현에 콱 박혀 교체·테스트 불가. DI+인터페이스면 가짜(mock) 주입해서 컨트롤러만 단위 테스트 가능.
- 타입은 인터페이스(`ReservationService`), 주입은 구현체(`ReservationServiceImpl`) → 인터페이스에 의존해 구현 교체해도 컨트롤러 불변. (Service 인터페이스+Impl 분리 이유)
- **왜 필드주입(@Autowired) 대신 final+생성자주입?** ①불변 안전 ②의존성 누락을 초기에 발견 ③테스트 쉬움. 스프링 권장.
- 면접 한 줄: "DI는 객체 생성·조립 책임을 컨테이너에 넘겨 결합도를 낮추고, 빈 재사용·구현 교체·단위 테스트를 쉽게 한다."

### E. JSP→Thymeleaf 전환 시 컨트롤러/서비스를 왜 안 바꾸나 (레이어 분리)
- 전환은 뷰 레이어만 바뀜. 컨트롤러는 "뷰 이름 + 모델"만 반환, 렌더링은 ViewResolver가 담당 → JSP든 Thymeleaf든 컨트롤러/서비스/매퍼 그대로 재사용.
- 공존 메커니즘: JSP resolver(/WEB-INF/views/, .jsp)와 Thymeleaf(templates/, .html)가 같이 있고, 전부 전환 후 JSP 의존성 제거.
- 면접: "관심사 분리 덕에 뷰 기술을 통째로 교체해도 비즈니스 로직 무수정."

### F. 헷갈렸던 점 (보강 필요)
- **뷰 이름 반환 vs `@ResponseBody`**: `@ResponseBody` 없으면 반환 String=뷰이름(HTML 렌더), 있으면 반환 객체=JSON 본문. POST createRes는 @ResponseBody로 Map→JSON. 성공/실패 둘 다 JSON으로 나감(에러 전용 아님). 이유는 AJAX가 데이터를 받아야 해서.
- **"DB 데이터" vs "에러 메시지"**: 사용자에게 뜨는 '이미 예약된 테마입니다'는 조회 데이터가 아니라 프로시저가 RAISE_APPLICATION_ERROR로 던진 거부 사유.
- **JSP 렌더링 vs JS가 뿌리는 것**: alert(res.message)는 JSP가 아니라 페이지의 자바스크립트(AJAX success 콜백)가 함. AJAX는 페이지 새로고침 없이 JSON만 받아 JS가 처리.
- 경로 한 줄: 프로시저 RAISE → DataAccessException(스프링 예외변환) → 컨트롤러 파싱 → JSON message → JS alert.

### G. Thymeleaf 핵심 오해 (보강 — 실수함)
- **`th:text`/`th:value`/`th:src` 는 "태그"가 아니라 "기존 HTML 태그 안에 붙이는 속성(attribute)"**. `<th:text=...>` 같은 새 태그 만들면 틀림. 올바른 형태: `<p th:text="${x}">placeholder</p>`. 닫는 태그 필요 없음.
- 값은 반드시 `${...}` 로 감싸야 꺼내짐. `th:text="x.y"`(글자) vs `th:text="${x.y}"`(값).
- 전용 단축키(th:text/value/src/href) 없는 커스텀 속성(data-*)만 만능 `th:attr` 사용. 예: 버튼 data-party-id.
- 면접: "Thymeleaf 동작 방식?" → "표준 HTML 태그에 th:* 속성을 더해 서버에서 값으로 치환. 정적으로도 열리는 natural template."

### H. 폼 제출 vs AJAX (예약 확정 버튼)
- 일반 폼 제출(`type=submit`): 브라우저가 폼 통째 전송 → 서버가 새 페이지(HTML) 응답 → 전체 새로고침/이동.
- AJAX: JS가 백그라운드 요청 → 서버가 JSON만 응답 → 새로고침 없이 JS가 alert+조건분기 처리.
- 예약은 서버가 @ResponseBody로 JSON 반환 + 성공/실패 메시지 alert + 결과에 따라 다른 페이지 이동 → AJAX 필수. 폼 제출이면 JSON이 빈 화면에 그대로 출력됨.
- 버튼이 `type="button"`인 이유: 폼 자동 제출을 막고 JS가 클릭을 가로채 AJAX 호출. 이 화면 `<form>`은 readonly 표시용(거의 장식), 실제 전송은 partyId 하나(AJAX).
- 한 줄: "화면 전체 새로 그릴 거면 폼 제출, 일부만/결과 분기면 AJAX."
