## 오늘 배운 핵심 개념 (면접용)

### A. 인증(Authentication) vs 인가(Authorization)
- 인증 = "너 누구냐". 로그인 여부. 사이트 전체에 한 번.
- 인가 = "그걸 네가 만져도 되냐". **대상이 있어야 성립**. 요청마다, 데이터 한 건마다.
- 권한 3부품: 주체(누가) × 동작(무엇을) × **대상(어느 것에)**.
  우리 코드는 `AuthUtil.checkOwner` 로 주체·동작만 보고 대상을 안 봤다 → IDOR.
- 옆 카페 사장도 진짜 OWNER 라서 역할 검사는 통과한다. 역할만 보면 "사장이면 아무 카페나"가 된다.
- 면접: "인증은 로그인 여부라 한 번만 확인하면 되지만, 인가는 '이 데이터가 이 사람 것인가'라서
  요청마다 대상을 놓고 확인해야 합니다. 저희는 역할 검사만 있고 대상 검사가 없었습니다."

### B. 값의 출처 = 신뢰도 (오늘 제일 크게 틀린 부분)
- `@RequestParam` = 브라우저가 보낸 값. 개발자도구로 얼마든지 바꾼다. **못 믿음.**
- `HttpSession` = 서버가 들고 있는 값. **믿음.**
- 규칙: **"누구인지"는 절대 파라미터로 받지 않는다. 세션에서 꺼낸다.** 파라미터는 "무엇을"만.
- 비교 공식: `[DB에서 꺼낸 그 물건의 주인]` vs `[세션의 나]` — 두 값의 출처가 서로 달라야 비교가 성립.
- 내가 처음에 `loginUserId = cafe.getUserId()` 라고 썼는데, 이건 세션 값을 DB 값으로 **덮어쓴** 것.
  자물쇠를 달고 열쇠를 그 문에서 꺼내온 셈 → 항상 열린다.
- 화면 방어는 방어가 아니다. 드롭다운에 내 카페만 담아도 POST 는 손으로 만들 수 있다.

### C. 3층 방어 (같은 검사를 어디에 두나)
```
컨트롤러  checkOwner()          "너 사장이냐"      역할만. 그대로 둠
서비스    assertOwnCafe()       "이거 네 카페냐"   예외 + 로그 (이유를 알려주는 층)
SQL       WHERE USER_ID = 주인  0건 INSERT        절대 안 뚫리는 층
```
- 컨트롤러에 안 넣은 이유: `AuthUtil` 호출처가 14곳인데 다수가 cafeId 자체를 안 갖고 있다.
  그리고 매번 하는 싼 검사(세션)와 가끔 하는 비싼 검사(DB)를 한 함수에 묶으면 안 된다.
- 심층 방어는 **층마다 다른 일을 할 때만** 유효. 같은 일을 두 번 하면 그냥 나쁜 중복.

### D. `INSERT ... SELECT` 로 SQL 층에서 막기
```sql
INSERT INTO MANAGER_HISTORY (...)
SELECT SEQ.NEXTVAL, #{cafeId}, #{userId}, 1
  FROM CAFE
 WHERE CAFE_ID = #{cafeId} AND USER_ID = #{ownerUserId}
```
- `VALUES` 뒤에는 WHERE 를 못 붙인다. SELECT 로 바꾸면 조건을 걸 수 있다.
- 내 카페면 1건 조회 → 1건 INSERT / 남의 카페면 0건 조회 → **아무 일도 안 일어남**.
- **함정: 0건 INSERT 는 예외가 아니다.** SQL 입장에선 "0줄 넣기 성공". 조용히 막히고 로그도 안 남는다.
  → 매퍼 반환을 `void` → `int` 로 바꿔 행 수를 확인하고 0이면 직접 던진다.
- 한 줄: **"막는 것"과 "막힌 걸 아는 것"은 별개다.**
- 검사와 실행이 SQL 한 문장 안에 있어서 그 사이에 끼어들 틈(TOCTOU)도 없다.

### E. Long 비교는 `equals`
- `Long` 은 숫자가 아니라 **객체**. `==` 는 "값이 같냐"가 아니라 "같은 상자냐"를 묻는다.
- 자바가 -128~127 만 상자를 재활용 → **userId 127번까지 잘 되다가 128번부터 갑자기 false.**
- 테스트에선 통과하고 운영에서 터지는 전형. `.equals()` 를 쓴다.

### F. 자잘한 것들
- 가드(guard clause) — 이상한 경우를 앞에서 먼저 쳐내고 정상만 아래로 흘린다. `AuthUtil.checkOwner` 도 같은 모양.
- 메서드 이름: `check~` 는 확인해서 결과를 돌려주는 느낌, `assert~` 는 아니면 여기서 멈춘다는 뜻. 이름이 동작을 말해야 한다.
- `||` 단축 평가 — 앞이 참이면 뒤를 아예 평가 안 한다. `cafe == null` 을 앞에 둬야 뒤의 `cafe.getUserId()` 에서 NPE 가 안 난다.
- `@RequiredArgsConstructor` = 롬복이 `final` 필드를 받는 생성자를 자동 생성 → 필드 한 줄 추가하면 스프링이 알아서 주입(생성자 주입).
  생성자 주입을 쓰는 이유: `final` 로 못 바꾸게 되고, 주입 실패면 앱이 아예 안 떠서 실행 전에 문제를 안다.
- 예외 처리 위치 — 인가 실패는 DB 오류가 아니다. 같은 try-catch 로 묶으면 나중에 구분이 안 된다. 검사는 `try` **밖**에.

### G. 탈퇴 처리 — 상태 컬럼을 안 만든 이유
- 탈퇴 시 `USER_INFO` 행을 지우고 `USER_DROP` 으로 옮긴다. `USER_ACCOUNT` 는 FK 때문에 못 지운다.
- 그래서 **`USER_INFO` 가 있냐 없냐가 곧 탈퇴 여부**다. 별도 STATUS 컬럼을 만들면 진실이 두 군데 생겨 어긋난다.
  (학원에서 배운 "상태는 직접 구할 수 있으면 만들지 마라" = Single Source of Truth)
- 아이디찾기·비번찾기는 이미 `JOIN USER_INFO` 로 걸러내고 있었는데 **로그인과 `findByLoginId` 만 빠져 있었다.**
- `findByLoginId` 가 안 걸러서 → 탈퇴한 사람을 매니저로 등록할 수 있었다.
  매니저 뷰가 `LEFT JOIN USER_INFO` 라서 목록엔 **이름·전화 빈칸**으로 뜬다.
- 탈퇴자 로그인 시 "탈퇴한 계정입니다"가 아니라 "아이디 또는 비밀번호가 올바르지 않습니다"가 뜨는데,
  이게 오히려 맞다 → **계정 열거(account enumeration) 방어.** 실패 사유를 구분해주면 그 자체가 정보 유출.

## 오늘 관찰된 내 약점 (고치는 법)
- **인증/인가 구분이 아직 안 잡힌다.** 지난 세션에 이어 오늘 3줄 요약에서도 1번을 못 썼다.
  → 추상적으로 외우려 하지 말고 `checkOwner` vs `assertOwnCafe` 두 함수 이름으로 붙잡을 것.
- **`=` 대입과 비교를 헷갈린다.** `loginUserId = cafe.getUserId()` 로 써서 검사를 무력화시켰다.
  → "왼쪽에 오른쪽을 **넣는다**". 비교는 `==` / `equals`. 세션에서 온 값은 끝까지 안 건드린다.
- **null 체크 문법이 안 나온다.** `if (cafe!)` 라고 썼다. `!` 는 boolean 앞에만. 객체는 `== null` / `!= null`.
- **객체를 안 붙이고 메서드를 부른다.** `get.userId()` → `cafe.getUserId()`. "누구한테 물어보나"를 먼저.
- 잘한 것: `||` 로 두 가드를 합친 것, SQL 층에도 같은 조건을 넣어야 한다는 걸 스스로 말한 것,
  "서비스에서는 에러 메시지도 보내야겠네"까지 간 것. 두 층이 하는 일이 다르다는 걸 잡았다.
