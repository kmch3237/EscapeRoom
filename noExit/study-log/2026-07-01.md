## 오늘 배운 핵심 개념 (면접용)

### A. 폼 커맨드 객체 바인딩 (@ModelAttribute)
- POST 컨트롤러가 `enroll(Cafe cafe)`처럼 객체를 받으면, 스프링이 input의 `name` 속성을 커맨드 객체의 같은 이름 필드에 setter로 자동 바인딩.
- 그래서 `<input name="cafeName">` → `cafe.setCafeName(값)`. name이 필드명과 정확히 일치해야 담김(안 맞으면 null).
- 면접: "폼 데이터가 어떻게 자바 객체가 되나?" → "input name과 커맨드 객체 필드명을 스프링이 매칭해 @ModelAttribute로 자동 바인딩."

### B. th:object / th:field / th:errors + Bean Validation (풀세트) vs plain 폼
- **풀세트 3조각** (enrollForm이 이 방식):
  1. DTO에 검증 규칙: `@NotBlank @Pattern @Size @Email` (Bean Validation). 공유 도메인(User) 오염 막으려 별도 UserEnrollForm DTO 사용.
  2. 컨트롤러: GET이 빈 객체를 model에(`addAttribute("enrollForm", new UserEnrollForm())`), POST가 `@Valid @ModelAttribute + BindingResult`로 검증, `result.hasErrors()`면 폼으로 되돌림.
  3. 화면: `th:object="${enrollForm}"` + `th:field="*{loginId}"`(id·name·value 자동생성) + `th:errors="*{loginId}"`(필드별 에러).
- **`*{}` vs `${}`**: `*{loginId}`=th:object의 loginId(짧게), `${enrollForm.loginId}`=전체경로. th:object 있으면 `*{}`로 축약.
- **풀세트의 이득**: 검증 실패 시 입력값 유지 + 필드별 에러 표시.
- **plain 폼(cafeEnrollForm)을 쓰는 이유**: 검증 DTO 없음 / GET이 빈 객체 안 넘김 / @Valid·BindingResult 없음 / 필드별 에러 없음(일반 errorMessage 하나). Cafe에 검증 붙이면 공유 도메인 오염. → `name=` 커맨드 바인딩만으로 충분.
- 한 줄: **"검증+에러표시+값유지 필요하면 풀세트(th:object/field/errors+@Valid), 단순 폼이면 plain input."**
- 면접: "th:field 언제 쓰나?" → "커맨드 객체 + Bean Validation과 함께. name/value 자동생성 + th:errors 필드별 메시지 + 입력값 유지. 단순 폼엔 불필요."

## 관찰된 약점 / 습관
- th:object/th:field 개념을 다시 헷갈림(어제 enrollForm에서 썼는데 기억 못 함) → 반복 노출 필요.
- 페이징 로직을 아직 스스로 못 짬. 근본 원인=본인 표현: "이 클래스가 왜 필요한지 몰라서 감이 안 온다"(서비스에서 어떻게 쓰는지 그림 부재). 공식보다 "무엇을 위한 물건인지"를 먼저 잡아야.
- 입력 vs 출력(재료 vs 결과) 구분 또 흔들림: `page(int size, int totalPage)`에서 결과인 페이지수를 파라미터로 받으려 함. 재료는 dataCount.
- `%`(나머지) vs `/`(몫) 여전히 혼동. 삼항 조건에 항상 참인 `>=0` 씀(원하는 건 `%>0`).
