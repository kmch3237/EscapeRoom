## 오늘 배운 핵심 개념 (면접용)

### A. 폼 커맨드 객체 바인딩 (@ModelAttribute)
- POST 컨트롤러가 `enroll(Cafe cafe)`처럼 객체를 받으면, 스프링이 input의 `name` 속성을 커맨드 객체의 같은 이름 필드에 setter로 자동 바인딩.
- 그래서 `<input name="cafeName">` → `cafe.setCafeName(값)`. name이 필드명과 정확히 일치해야 담김(안 맞으면 null).
- 면접: "폼 데이터가 어떻게 자바 객체가 되나?" → "input name과 커맨드 객체 필드명을 스프링이 매칭해 @ModelAttribute로 자동 바인딩."

### B. th:object / th:field / th:errors + Bean Validation (풀세트) vs plain 폼
- **풀세트 3조각** (enrollForm이 이 방식):
  1. DTO에 검증 규칙: `@NotBlank @Pattern @Size @Email` (Bean Validation). 공유 도메인(User) 오염 막으려 별도 UserEnrollForm DTO 사용.
  2. 컨트롤러: GET이 빈 객체를 model에(`addAttribute("enrollForm", new UserEnrollForm())`), POST가 `@Valid @ModelAttribute + BindingResult`로 검증, `result.hasErrors()`면 폼으로 되돌림.
  3. 화면: `th:object="${enrollForm}"` + `th:field="*{loginId}"`(id·name·value 자동생성) + `th:errors="*{loginId}"`(필드별 에러).
- **`*{}` vs `${}`**: `*{loginId}`=th:object의 loginId(짧게), `${enrollForm.loginId}`=전체경로. th:object 있으면 `*{}`로 축약.
- **풀세트의 이득**: 검증 실패 시 입력값 유지 + 필드별 에러 표시.
- **plain 폼(cafeEnrollForm)을 쓰는 이유**: 검증 DTO 없음 / GET이 빈 객체 안 넘김 / @Valid·BindingResult 없음 / 필드별 에러 없음(일반 errorMessage 하나). Cafe에 검증 붙이면 공유 도메인 오염. → `name=` 커맨드 바인딩만으로 충분.
- 한 줄: **"검증+에러표시+값유지 필요하면 풀세트(th:object/field/errors+@Valid), 단순 폼이면 plain input."**
- 면접: "th:field 언제 쓰나?" → "커맨드 객체 + Bean Validation과 함께. name/value 자동생성 + th:errors 필드별 메시지 + 입력값 유지. 단순 폼엔 불필요."

### C. HTTP 요청/응답, 응답 본문, @ResponseBody (★기본)
- HTTP 응답 = 택배 상자. 헤더(송장: 상태코드·콘텐츠타입=메타) + 본문(body, 내용물=실제 데이터).
- "응답 본문에 실어 보낸다" = 상자 안에 데이터를 담아 보낸다.
- `@ResponseBody` 없음: `return "뷰이름"` → 스프링이 JSP/HTML 렌더링해 완성 HTML을 본문에 담음.
- `@ResponseBody` 있음: `return list`(자바 객체) → 뷰 안 찾고 Jackson이 JSON으로 변환해 본문에 담음. (list는 화면이 아니라 데이터 덩어리!)
- 비유: JS가 "완성 요리(HTML) 말고 재료(JSON)만 봉투에 담아 달라"(AJAX) → 서버는 데이터만, 화면 그리기는 JS(renderParty).

### D. GET vs POST (실무/면접)
- 용도가 본질: **GET=조회/읽기, POST=생성·변경·제출(서버 상태 바꿈)**. 나머지는 파생.
- 데이터 위치: GET=URL 쿼리스트링(`?kwd=`, 노출), POST=본문(URL에 안 보임).
- GET: 북마크·공유·캐시 가능, 새로고침 안전, 멱등(여러 번=같음), URL 길이 제한.
- POST: 북마크X·캐시X, 새로고침 시 재전송(중복 위험), 본문이라 대용량 가능.
- 비유: GET=도서관 책 찾아보기(안 바뀜), POST=서류 제출(서버 바뀜, 중복 주의).
- **"POST가 보안?"** = 반만 맞음. URL 노출은 피해서 비번은 POST. 하지만 본문도 그대로 보임(F12/프록시) → 전송 보안은 **HTTPS**가 담당. POST≠암호화.
- **"다 POST?"** 안 되는 이유: ①GET=조회 약속 깸(브라우저·검색엔진·캐시 오해) ②캐시·성능 손해 ③북마크·공유 불가 ④삭제를 GET으로 하면 크롤러가 링크 눌러 다 삭제된 실제 사고 → 변경은 POST ⑤REST 규약(조회GET/생성POST/수정PUT/삭제DELETE).
- 원칙: **읽기=GET, 쓰기=POST (보안 아니라 용도로 구분)**.
- 이 프로젝트 관찰: POST /party/list는 사실 조회인데 POST 사용(필터 많아 관례). 엄밀히는 순수 조회라 GET이 더 규약에 맞음 → 면접 포인트.

### E. MyBatis 매퍼 인터페이스 ↔ XML 연결
- 매퍼 인터페이스엔 메서드 시그니처만(SQL 없음). SQL은 XML에.
- 연결: XML의 `namespace` = 매퍼 인터페이스 전체경로, `<select id="...">`의 id = 메서드명. MyBatis가 구현체를 프록시로 자동 생성.
- resultType: 컬럼 별칭(AS)을 DTO 필드명과 맞추면 자동 매핑(+map-underscore-to-camel-case). 복잡 매핑(1:N 등)만 resultMap.

### F. 복잡 쿼리 짜는 6단계 사고법 (파티 목록으로 연습)
- ① 결과 정의(SELECT 뭐?) ② 출처(어느 테이블) ③ 연결(JOIN 경로 FK=PK) ④ 요약(집계=서브쿼리) ⑤ 조건(WHERE) ⑥ 정렬/제한. **결과에서 거꾸로 출발**.
- JOIN 경로: PARTY→PARTY_ROOM(연결테이블)→RES_OPEN→ROOM. JOIN ON은 `A.공통 = B.공통`(서로 다른 두 테이블).
- 집계 서브쿼리(파생테이블): `SELECT PARTY_ID, AVG(AGE) avgAge... FROM ... GROUP BY PARTY_ID`. **GROUP BY 기준은 SELECT에도** 넣어야(식별+조인용). `AVG(재료AGE) AS 결과이름avgAge`(재료 vs 결과 구분).
- **부품 조립**: STEP1(뼈대 메인)에 STEP2를 `JOIN ( 서브쿼리 ) E ON P.PARTY_ID=E.PARTY_ID` 로 "한 줄 더" 추가. JOIN=두 쿼리 접착이 아니라 한 쿼리에 테이블 추가. 서브쿼리 안엔 `;` 없음, 문장 끝에 하나.
- WHERE 위치: FROM~JOIN 다음, ORDER BY 앞. 여러 조건 AND. LIKE는 `컬럼 LIKE '%키워드%'`(%=와일드카드). 커서 페이징 `id < 마지막id` + `ORDER BY id DESC FETCH FIRST 4 ROWS ONLY`.

### G. 파티 상세: @PathVariable / RedirectAttributes / 1:N
- `@PathVariable`=경로값(`/info/5`의 5, 주로 리소스 id) vs `@RequestParam`=쿼리스트링(`?kwd=`).
- `RedirectAttributes`(어노테이션 아님, 파라미터 객체): 리다이렉트는 브라우저가 **새 요청**을 보내는 것이라 일반 Model은 날아감 → RedirectAttributes(flash)로 넘김. forward=같은요청(model 유지) vs redirect=새요청(안 유지).
- 1:N(파티1-파티원N): 이 프로젝트는 `<collection>` resultMap 대신 **쿼리 2개로 분리**(getPartyById+getPartyCrewList). 장점: 파티원 자주 변해 부분 재조회 쉽고 쿼리 단순. (대안=collection: 왕복1번but 설정복잡·부모컬럼 중복). association=1:1, collection=1:N.
- 같은 뷰 VW_PARTY_ACTIVE_MEMBER를 목록=집계(AVG/COUNT), 상세=멤버 개별나열 두 용도로.

### H. 검증 위치 & 방어적 계층화 (예약 vs 파티신청)
- 예약=프로시저(PL/SQL)에서 검증+FOR UPDATE 동시성+트랜잭션. 파티신청=자바 컨트롤러에서 순차 검증 후 insert. **방식이 제각각=일관성 아쉬움**.
- **fat controller 안티패턴**: 검증 6개가 컨트롤러에 있음 → 비즈니스 규칙은 **서비스 레이어**로 내려야. 컨트롤러는 얇게(요청/응답만).
- **방어적 계층화(defense in depth)**: 층마다 **다른 종류** 검사 — JS(UX)/컨트롤러·DTO(형식 @Valid)/서비스(비즈니스 규칙)/DB(UNIQUE·FK·락=최종 정합성). "같은 검사 복붙"이 아니라 관심사별 분담. 강사님 "둘 다 걸어라"=이 의미로 이해.
- **race condition(TOCTOU)**: 파티신청 `hasApply`(검사)와 `partyApply`(삽입) 사이 틈 → 동시 요청 시 중복 신청 가능. 예약의 FOR UPDATE 같은 락 없음. 개선=DB UNIQUE(PARTY_ID,USER_ID) 제약 또는 락으로 검사·삽입 원자화.
- 실무: 형식→DTO @Valid / 비즈니스→서비스 / 정합성·동시성→DB제약+트랜잭션. 층별 분담.

## 관찰된 약점 / 습관
- th:object/th:field 개념을 다시 헷갈림(어제 enrollForm에서 썼는데 기억 못 함) → 반복 노출 필요.
- 페이징 로직을 아직 스스로 못 짬. 근본 원인=본인 표현: "이 클래스가 왜 필요한지 몰라서 감이 안 온다"(서비스에서 어떻게 쓰는지 그림 부재). 공식보다 "무엇을 위한 물건인지"를 먼저 잡아야.
- 입력 vs 출력(재료 vs 결과) 구분 또 흔들림: `page(int size, int totalPage)`에서 결과인 페이지수를 파라미터로 받으려 함. 재료는 dataCount.
- `%`(나머지) vs `/`(몫) 여전히 혼동. 삼항 조건에 항상 참인 `>=0` 씀(원하는 건 `%>0`).
