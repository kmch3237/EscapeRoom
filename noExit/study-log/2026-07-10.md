- 매퍼 파라미터 3방식(Map / @Param / DTO) 정리 + Map↔DTO 상호 변환 직접 연습.

## 오늘 배운 핵심 개념 (면접용)

### A. 매퍼에 값 넘기는 3가지 방식 (Map / @Param / DTO)
- MyBatis 매퍼 메서드는 파라미터가 사실상 1개 → 값 여러 개는 하나로 묶어야 함.
- **Map**: `map.put("userId", ..)` → 인터페이스 `void m(Map map)`. 간단하나 키 오타는 런타임에 터짐.
- **@Param**: `void m(@Param("userId") Long a, @Param("resOpenId") Long b)`. 값 2~3개일 때.
- **DTO**: `void m(OpenReservationForm form)`. 필드 많은 폼에 적합, 컴파일 체크됨.
- **★핵심: 셋 다 XML은 `#{userId}` 그대로.** MyBatis가 Map이면 key, DTO면 getter, @Param이면 그 이름으로 찾음. 바뀌는 건 "담는 그릇"과 "인터페이스 타입"뿐. (넘기는 그릇 = 인터페이스 타입, 무조건 Map 아님)
- 면접: "파라미터 여러 개 어떻게 넘기나?" → "Map/DTO로 묶거나 @Param으로 이름 붙임. XML은 #{}로 동일하게 꺼냄."

### B. 인증(Authentication) vs 인가(Authorization)
- **인증 = 너 누구야(신원)** → 세션에서 userId 꺼냄. 세션은 웹 개념이라 컨트롤러가 함.
- **인가 = 너 이거 해도 돼(권한)** → "이 슬롯 네 것 맞아?" 판단. 이 프로젝트는 프로시저가 함(원칙상 서비스).
- 세션 ≠ 권한. 세션은 신원만 담음. (회사 건물: 출입증=인증 / 사장실 열 자격=인가)
- **★클라이언트에서 오는 값은 절대 신뢰 안 함.** userId를 브라우저 파라미터로 받으면 조작(개발자도구/curl)해서 남의 것 삭제 가능 → 신원은 반드시 세션에서.
- 면접: "인증과 인가 차이?" → "인증은 누구인가(세션 확인), 인가는 무엇을 할 수 있나(권한 판단)."

### C. 비즈니스 로직 위치: DB 프로시저 vs 자바 서비스 (트레이드오프)
- 오픈/취소 = 로직이 프로시저 → 자바 서비스는 얇음(전달만), 트랜잭션도 프로시저가 COMMIT.
- 출석확정(finalize) = 로직이 자바 서비스 → 서비스 두꺼움(반복문/분기/다중 INSERT), 트랜잭션은 Spring `@Transactional`.
- **로직이 자바로 오면 트랜잭션 책임도 자바(@Transactional)가 짐.**
- 면접: "서비스가 왜 이렇게 얇아요?" → "로직을 DB 프로시저에 뒀기 때문. 원칙은 서비스지만 동시성 제어를 DB에서 하려는 선택."

### D. @Transactional — all-or-nothing
- `@Transactional(rollbackFor = Exception.class)`: 메서드 안 여러 INSERT를 하나로 묶음.
- 없으면 → 머리(ATTENDANCE)는 들어갔는데 상세(DETAIL) 일부만 들어간 "반쪽 데이터" 발생.
- 예약/결제/취소처럼 여러 테이블 바꾸는 로직에 필수.

### E. selectKey / OUT 파라미터 / resultType — DB가 자바로 값 돌려주는 3가지
- **selectKey (order=BEFORE)**: INSERT 전에 `SEQ.NEXTVAL` 뽑아 `keyProperty`로 DTO에 도로 심음. → `insertAttendance(head)` 후 `head.getAttendanceId()`가 값을 갖는 이유. (머리 PK를 상세 FK로 연결)
- **OUT 파라미터**: `#{newTemp, mode=OUT}` → 프로시저가 계산한 값을 자바로 돌려줌. (IN=넣기, OUT=받기)
- **resultType**: 조회 결과를 타입/DTO에 담아 반환.

### F. 마스터-디테일(1:N)과 이중 반복문
- ATTENDANCE(예약 1건=머리 1줄) : ATTENDANCE_DETAIL(손님 1명=상세 여러 줄) = 1:N.
- "여러 개(예약) 안에 여러 개(손님)" → 반복문 2겹. 바깥=예약별 머리 INSERT, 안쪽=손님별 상세 INSERT.
- 규칙: **여러 개 안에 여러 개 = 2겹.**

### G. 2단계 저장 패턴 (임시저장 → 확정)
- 출석: `saveDraft`(세션에 누적) → `finalize`(세션 꺼내 DB INSERT). 장바구니→결제.
- 세션의 두 용도: 신원(userId) + 작업중 임시 데이터(attendDraft).
- finalize 안 누르고 브라우저 닫으면 세션만 있다 사라짐 → DB엔 안 남음.

### H. 코드 재사용 (DRY)
- 사장 예약취소(`resDelete`)가 손님용 `myService.cancelReservation` + `PRC_RESERVATION_CANCEL` 재사용.
- 프로시저 내부 `FN_GET_RESERVATION_ROLE`이 예약자/사장 역할 판별 → 규칙 분기. 화면 달라도 취소 로직 하나.

## 오늘 관찰된 내 약점 (고치는 법)
- **데이터 흐름 추적 흔들림**: "담겼지만 안 쓰이는 값(잉여)"을 잡기 어려워함 → 값이 실제 어디서 꺼내 쓰이는지 끝까지 따라가기.
- **추상 설명 잘 안 먹힘**: 비유·실제 숫자를 줄 때 이해 → 새 개념은 항상 실제 값 하나 넣어 따라가기.
- **중첩 구조 추론 약함**: 이중 반복문 "왜 2겹?" → "여러 개 안에 여러 개 = 2겹" 암기.
- **읽기 O 쓰기 X**: 들으면 이해하나 직접 바꾸기 어려움 → 빈칸 채우기로 "쓰기" 연습 반복(오늘 인터페이스 타입 직접 맞힘, 개선 중).
